# Проверка качества смешанной базы знаний

Статус: инфраструктура оценки; не свидетельство готовности функциональности. Индекс и автоматические темы из встреч ещё разрабатываются.

## Зачем отдельная разметка

Нынешний smoke-тест считает пару релевантной по совпадению одной общей метки. Это подходит для обнаружения грубых ошибок модели, но не покрывает заметку с несколькими темами, похожие материалы разных проектов, отдельную встречу без подходящих соседей и субъективность разметки. Высокий precision среди выданных результатов без числа пустых ответов тоже не показывает полноту. Маленький синтетический holdout и его порог нельзя считать основанием для автоматического включения группировки.

## Корпус и протокол

- Создать раздельные calibration и holdout из разных проектов и разговоров; исключить дубликаты, производные тексты, переводы и соседние части одной встречи между выборками. Настройки и пороги фиксировать до анализа holdout. Для реальных материалов нужно отдельное согласие владельца и безопасное хранение; никакого чтения личной библиотеки или облачной отправки в тесте по умолчанию.
- Разметить допустимые связи вручную по каждому запросу, включая пары заметка–заметка, заметка–встреча, встреча–заметка, встреча–встреча и запросы без подходящих соседей. Включить русские/английские и смешанные тексты, длинные встречи, одинаковую лексику в разных проектах, разные формулировки одного факта, недоступные/устаревшие источники. Не сводить всё к одной метке документа.
- Минимум два независимых оценщика должны разметить спорные примеры; фиксировать разногласия и правила разрешения, чтобы не выдавать субъективную оценку за объективную истину. Малые или несбалансированные категории указывать явно и не переносить выводы на другие категории.
- Для каждой модели фиксировать её digest, размерность, версию токенизации и точный формат документа/чанкинга, индекс, алгоритм и corpus hash. Векторы должны быть сформированы тем же путём, что и в приложении; иначе результат не является проверкой продукта. Пересборка корпуса требует отдельной неизменяемой версии и не делает старый holdout новым.

Полная попарная разметка квадратична, поэтому этот формат предназначен для небольшого полностью размеченного gold-набора, а не для разметки всех пар библиотеки в 10 000 документов. Для масштабной оценки нужен отдельный воспроизводимый протокол: репрезентативная выборка запросов, объединённый пул кандидатов нескольких систем, слепая разметка и явный учёт неразмеченных пар. Неразмеченное нельзя считать отрицательным; оценки на разных пулах нельзя напрямую представлять как полные и сопоставимые.

`scripts/eval_knowledge_judgments.py` — офлайн-инструмент для оценки заданных векторов по явным суждениям. Документы имеют `id` и `type` (`note` или `meeting`); запрос ссылается на ID документа и содержит полные списки `relevant` и `irrelevant` для **каждого другого** документа. Неоднозначные пары сначала разрешаются в протоколе разметки, а не исключаются молча. Векторы задаются отдельно как `model`, `revision`, `vectors` (ID → массив чисел). Запуск с заранее зафиксированным порогом:

```sh
python3 scripts/eval_knowledge_judgments.py --corpus corpus.json --vectors vectors.json --threshold 0.43
```

Инструмент выводит precision среди выданных результатов, macro recall@k по запросам с релевантными соседями, покрытие таких запросов, долю ложных результатов на запросах без релевантных соседей и precision отдельно для направленных типов пар. Пустой знаменатель выводится как `null`, а не успех. Хеши фиксируют входы, но не доказывают репрезентативность корпуса и не подтверждают соблюдение раздельности наборов — это проверяется протоколом.

## Критерии приёмки

До изучения holdout команда фиксирует численные цели и минимальные размеры каждой категории, baseline, политику пустых ответов, допустимую ошибку на похожих разных проектах и критерии для автоматического показа. Общая цель precision@3 ≥85% из плана не заменяет отдельные ограничения по полноте и ложным связям; недостаточная выборка означает «не измерено». Измерять кластеризацию тем отдельно от поиска соседей: полноту включения, стабильность после небольших правок, качество названия и его обоснованность разрешёнными источниками. Отдельно проверять точность открытия источников, отзыв прав и нагрузку во время записи. Расчёт метрики этого скрипта сам по себе не включает функции и не означает прохождение приёмки.
