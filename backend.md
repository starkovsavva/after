# Архитектура backend After

Backend After — локальное прикладное ядро Rust и ограниченный Python-worker для
моделей и распознавания. Это часть настольного приложения без отдельного
постоянного web-backend. Swift управляет интерфейсом, жизненным циклом сценариев
и нативными службами; локальный OAuth callback остаётся механизмом авторизации.

Документ описывает рабочую архитектуру следующего обновления, включая новые имена
Swift-модулей. Это не список возможностей опубликованного релиза. Планы из
`docs/specs/` не считаются реализованными без подключённого входа и проверок.

При изменении сценария сохраняй существующее разделение: входной контракт,
доменные правила, хранение и внешние механизмы. Не переноси в After слои и
соглашения чужого framework только ради одинаковых названий файлов.

## Структура

```text
Sources/
  AfterCore/                  # общие значения, правила и форматирование
  AfterPlatform/              # контракты служб, worker/account/calendar DTO
  AfterLocalization/          # локализация и собственные ресурсы модуля
  AfterPlatformMacOS/          # реализация нативных механизмов
  AfterApp/                   # интерфейс и координация сценариев
rust-core/src/
  lib.rs                      # JSON-диспетчер и C ABI
  main.rs                     # CLI и входы MCP
  workspace_repository.rs     # канонический workspace и транзакции
  workspace_repository/       # операции базы знаний и пересборки заметок
  notes.rs, folders.rs         # заметки, вложения, папки и профили
  task_workspace.rs, cards.rs # задачи, контекст, история и карточки
  jobs.rs, worker.rs           # долговечная очередь и запуск обработки
  ai.rs, chatgpt.rs            # выбранный провайдер и запросы генерации
  knowledge_rebuild_ai.rs     # предложение пересборки без применения
  search.rs, semantic.rs       # текстовый и смысловой поиск
  knowledge.rs                # источники и проверяемый контекст ответа
  mcp.rs, scoped_share/        # доступ агента к разрешённым материалам
  media.rs                    # подготовка медиа через проверенный FFmpeg
  platform/macos/             # CPython host, embedded speech, IPC, APFS
backend/
  engine.py                   # ASR, разделение голосов, подготовка моделей
  embedded_bridge.py          # ограниченный вызов Python внутри процесса
  cloud_speech.py             # протокол облачного распознавания
  short_speech.py             # короткая диктовка
  media_runtime.py, models.py # модельная среда и проверка компонентов
  python-runtime.json         # закреплённая сборка CPython
scripts/, Tests/              # сборка, контрактные и сквозные проверки
```

Это карта существующих ответственностей, а не требование немедленно разбить
каждый файл на новые пакеты. Перенос выполняется вместе с законченным сценарием;
не оставляй вторую независимую реализацию тех же правил.

## Команды, чтение и точки входа

- **Rust-команды** владеют правилами изменения библиотеки, проверкой области,
  ревизий и согласованности. Основной JSON-вход — `request` в
  [lib.rs](rust-core/src/lib.rs). C ABI `posle_request` / `posle_free_string`
  возвращает JSON-envelope с `ok` и `value` либо `error`; Swift не разделяет
  с Rust layout структур или владение памятью моделей.
- **Чтение и поиск** возвращают данные или ссылки на источники в разрешённой
  области. Поисковый индекс производный; его результат проверяется по оригиналу
  до выдачи. Не прячь изменение заметки или запуск генерации внутри обычной выборки.
- **CLI и worker** в [main.rs](rust-core/src/main.rs) и
  [worker.rs](rust-core/src/worker.rs) выполняют длительные операции. Протокол
  прогресса — JSONL, включая `progress`, `done` и `error`; обычный диагностический
  вывод не должен повреждать stdout-протокол. Отдельные режимы — `mcp` и `mcp-share`.
- **Swift** в `AfterApp` сохраняет черновики, организует подтверждение, отмену,
  очередность и показ результата. Доменная проверка не заменяется отключённой
  кнопкой. `BackgroundJobs` и `JobExecution` управляют исполнителями, а не создают
  параллельную схему хранения задач.
- **Python** выполняет ASR, разделение голосов и модельные операции через
  проверенную среду. Новые правила workspace и SQL-доступ туда не переносятся.
  Существующие Python-операции с файлами встреч подчиняются проверкам публикации,
  путей и блокировок; это не второй владелец `core.sqlite`.

Не вводим обязательные Django-подобные `services/`, `selectors/`, ORM или классы
для каждой функции. В Rust сценарий может быть типизированной функцией и связанными
типами своего модуля. Чистое преобразование остаётся функцией; общий модуль
появляется при действительном переиспользовании.

## Зависимости и платформенные границы

Общие Swift-значения находятся в `AfterCore`. `AfterPlatform` зависит от них и
объявляет контракты без AppKit, ScreenCaptureKit, EventKit и `AppStore`.
`AfterLocalization` владеет переводами и ресурсным пакетом.
`AfterPlatformMacOS` реализует захват и воспроизведение, разрешения, календарь,
Keychain, авторизацию, процессы и Rust FFI. `AfterApp` выбирает реализации;
например, медиа собираются в `PlatformComposition.swift`.

Адаптер отвечает за нативный механизм и перевод его ошибок в контракт. Решение,
кому разрешена операция, что сохранить и когда показать результат, остаётся у
домена или координатора сценария. Нативные службы не импортируют приложение.
Не добавляй глобальный DI-контейнер или обход контракта ради одного вызова.

В Rust `platform/mod.rs` выбирает macOS-реализации runtime и транспорта.
Оставшиеся Unix-права, файловые дескрипторы, блокировки и процессы ещё требуют
работы для другой ОС. Условная сборка Swift-модулей и наличие Ubuntu CI не
означают готовность Linux/Windows-клиента или прохождение тестов на этих ОС.

## Хранение и транзакции

| Данные | Владелец и формат |
| --- | --- |
| Заметки, задачи, папки, связи и история | Rust, `core.sqlite`. |
| Операции workspace | Snapshot, entity revisions, receipts и outbox в одной SQL-транзакции. |
| Очередь обработки | Rust, отдельная `jobs.sqlite`; Swift управляет исполнением. |
| Медиа, транскрипты и конспекты встреч | Файлы встречи с проверяемыми версиями и публикацией. |
| Настройки и черновики интерфейса | Отдельные файлы; не все данные перенесены в workspace. |
| Поисковые индексы и embeddings | Производные данные, перестраиваемые из разрешённых источников. |
| Ключи и сессии | Нативное защищённое хранилище; в macOS — Keychain. |

[workspace_repository.rs](rust-core/src/workspace_repository.rs) фиксирует
агрегат, каталог сущностей, receipts и outbox совместно, с CAS и блокировкой
workspace. Ревизия защищает от перезаписи конкурентных правок. Неизвестные
совместимые поля сохранённых объектов не теряются при обновлении известных полей.

Старый `notes/workspace.json` импортируется один раз, исходные байты сохраняются.
После миграции JSON — производный экспорт, а не запасной источник истины.
Отсутствующая или повреждённая каноническая БД не заменяется им автоматически.
У очереди, индексов и некоторых подсистем собственные хранилища: нельзя заявлять
общую транзакцию для всей библиотеки и всех файлов.

Встроенный Python не открывает `core.sqlite` вторым SQLite-runtime внутри процесса,
который загрузил Rust C ABI. SQL-инспекция тестов выполняется отдельным процессом.
Проверки корней, обычных файлов и symlink-переходов выполняются до доступа к диску;
путь или идентификатор, предложенный моделью, не становится доверенным.

## Настройки, очередь и публикация

Профиль операции вычисляется из общих настроек и переопределений папки. Очередь
сохраняет снимок несекретных параметров, область, попытку и ревизию входных данных.
`POSLE_JOB_SETTINGS` и профиль папки описывают конкретный запуск; они не дают
разрешение продолжать после отзыва доступа. Текущие feature-права проверяются заново.

До внешнего запроса и публикации результата проверяются профиль и исходные данные.
Смена модели, папки или источника не должна позволять старому ответу заменить новый
результат. Отмена распространяется на subprocess и локальную аренду runtime;
поздний callback не оживляет завершённый запрос. Неопределённый или прерванный
платный запрос не повторяется автоматически как будто ничего не произошло.

Новые журналируемые изменения используют существующие CAS и `operationID`:
идентичный повтор возвращает прежний результат, другая полезная нагрузка с тем же
ID отклоняется. Undo проверяет версии затронутых объектов и сохраняет чужие
последующие правки. Не держи SQL-транзакцию открытой во время сетевого запроса.

Пример разделения — пересборка заметок: prepare фиксирует выбранные источники,
генерация создаёт предложение, preview проверяет его, apply выполняет явное
подтверждённое изменение, undo проверяет возможность отката. Модель не применяет
предложение сама. Контракт и лимиты развиваются вместе со сценарием в
`docs/specs/knowledge-rebuild.md` рабочей ветки.

## Поиск, MCP и недоверенные данные

Локальный поиск, отправка источника модели и доступ внешнего агента — разные
разрешения. При живом поиске на выдаче повторно проверяются источник, его
актуальная версия, область и разрешение. Индекс и кэш не заменяют эту проверку.
Отсутствие embeddings оставляет текстовый поиск; это не доказательство
качества смысловых связей. Смена embedding-модели не смешивает разные поколения.

У MCP есть разные контуры: task MCP работает с явно открытыми задачами и
материалами; `mcp-share` — с одобренным неизменяемым снимком конкретного
подключения. Изменения оригинала не обновляют переданную копию. Отзыв или истечение
снимка запрещают дальнейшую выдачу, но не могут отозвать уже полученные данные.
Агент не может сам одобрить снимок или расширить его область.
Внутренний `scoped_agent` остаётся закрытым прототипом без публичного маршрута:
его наличие не означает включённый live-поиск агента по всей библиотеке.

Тексты заметок, встреч, кода и артефактов — недоверенное содержимое. Они не
задают команды компьютера, не меняют права и не разрешают облачный запрос.
Модель получает ограниченный контекст и возвращает проверяемые значения;
реальные ID, маршруты, файловые ограничения и публикацию контролирует код.
Свежая ссылка на источник сама по себе не доказывает фактическую точность ответа.

## Runtime, секреты и совместимость

Release-приложение проверяет встроенный digest окончательно подписанной
Rust-библиотеки до `dlopen`. CPython проверяется по закреплённому архиву и
встроенному инвентарю. Проверки идентичности открытых файлов сохраняются до
выполнения кода; они не гарантируют защиту от локального процесса того же
пользователя, одновременно переписывающего уже открытый inode.
Транспорт embeddings проверяет владельца живого процесса и сокета. DEBUG-подмены
не становятся допустимыми release-настройками. Полного hash lock всех pip/MLX/ONNX
зависимостей пока нет; закрепление CPython не означает проверку всей цепочки поставки.

Секреты передаются существующим механизмом выбранного подключения. Они не
попадают в workspace, настройки задания, аргументы командной строки или логи.
Не меняй подключение пользователя и не создавай новый ключ ради теста с mock-провайдером.

Исторические `app.posle.meetings`, `POSLE_*`, URL-схемы, Keychain-идентификаторы,
пути библиотеки, crate/CLI и C ABI сохраняются для совместимости. Переименование
Swift-модуля в After не является разрешением менять сохранённые ID или формат БД.
При изменении миграции проверяй также совместимость со старыми писателями,
очередью и файлами встреч; одного теста чтения новой версией недостаточно.

## Типизация и проверки

Новый код использует явные Rust/Swift-типы входов и результатов и типизированные
параметры Python по мере изменения сценария. В проекте остаются JSON-команды на
`serde_json::Value`: валидируй их в существующей границе, не выдавай их за уже
полностью типизированный API. Закрытые наборы значений оформляй enum, сохраняя
значения на диске и в протоколе. Неизвестные внешние значения обрабатывай явно.

Подготовка среды и детали профилей — в [документации разработки](docs/development.md).

```sh
python3 scripts/verify.py --list
cargo test --manifest-path rust-core/Cargo.toml --locked
python3 scripts/check_platform_boundaries.py
python3 scripts/verify.py quick
python3 scripts/verify.py integration
python3 scripts/verify.py native
```

`quick` собирает Swift и проверяет Swift/Python/Rust-контракты. `integration`
проверяет настоящие CLI/FFI и локальные протоколы на синтетических данных.
`native` требует активную графическую сессию Mac и запускает UI-сценарии
последовательно. Тестовый Python выбирается через `POSLE_PYTHON` после подготовки
зависимостей; Command Line Tools используют standalone core-проверки без XCTest.

Для изменения сценария проверяй его настоящий вход, ошибку/отмену, конкурентное
изменение и сохранённый результат. Провайдеры и устройства подменяются на своих
границах. Физические Bluetooth/USB, качество реальной модели и установка точного
пакета проверяются отдельно. Успех синтетического теста не заменяет эти проверки.
Фиксируй точную сборку и исполненные команды, а не обещание «все тесты проходят».

Документация и техническая реорганизация не являются выпуском. Сборка, упаковка,
подпись, установка и публикация выполняются отдельными существующими скриптами;
этот документ не разрешает запуск публикации или изменение release notes.
